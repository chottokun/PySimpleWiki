# SimpleWiki Python版 移植計画メモ

作成日：2026-11-12  
状態：計画のみ。コード作成、リポジトリ作成、git/gh の書き込みは行っていない。
決定（2026-11-13、のぶひこ）：**置き場所は別リポジトリ**（pat-okf-agent 内でも本家リポジトリ内でもない）。リポジトリ名は **PySimpleWiki** に確定（同日）。リポジトリ作成と最小足場の構築を同日開始。共有検索コアの切り出し時期など残りの論点はメモ内のとおり。

## 0. 前提と調査範囲

- 本家は、のぶひこ自身の GitHub リポジトリ [SimpleWiki](https://github.com/chottokun/SimpleWiki)。PowerShell 製で、OKF v0.2 対応のローカル Wiki サーバー、静的 HTML 出力、LLM RAG を備える。
- 本メモでは、調査時点の本家 `main`（commit `df9cb68`）の README、`AGENTS.md`、`lib/`、ルートスクリプト、テスト構成を読んだ。
- 移植対象は本家のコードそのものではなく、**OKF の読み方、並べ方、探し方、公開 API の考え方**である。PowerShell / Windows 固有の実装は Python と Linux の部品へ置き換える。
- Python を選ぶ理由は、pat-okf-agent と検索・文書モデルを共有でき、サードやシャナの VM など Linux 環境でそのまま動かせるため。
- pat-okf-agent の検索再設計メモ `plan/okf-search-redesign-design-2026-11-12.md` は、本メモ作成環境からは参照できなかった。したがって本メモでは、**検索コアは再設計と共有する前提**だけを置き、再設計メモで確定する数値や API を先取りしない。

### 1.2 本家の設計で特に引き継ぐもの

1. **順序はファイル名ではなく `index.md` が決める。** Python版でも表示順の正本を変えない。
2. **重みは一致した場所につく。** タイトル、タグ、概要、本文という一致の証拠の違いであり、概念そのものの重要さではない。
3. **本文の頻度は頭打ちにする。** 長い文書や資料ノートが頻度だけで概念ノートを埋めない。
4. **API を閲覧 UI と分ける。** `/api/index.json` と `/api/chunks.json` があれば、ビューア、RAG、外部ツールが同じ土台を使える。
5. **読み取り専用を守れる。** エディタを切ると UI と API の両方で書き込みを止める考え方は、KB を安全に開くうえで重要である。

## 2. 段階分け

### 第0段：互換性の物差しを固定する

実装の前に、本家の振る舞いを Python 側の受け入れ条件へ変換する。

- 本家の Pester テストから、メタデータ、表示順、検索、API の代表ケースを抽出する。
- 本家サンプル `markdown_sample/` と現在の OKF KB を、同じ入力フィクスチャとして扱えるようにする。
- `/api/index.json` と `/api/chunks.json` の項目、欠損時の補完、並び順を文書化する。
- 互換性の範囲を決める。目指すのは「同じ KB を同じ順序で読み、同じ API 形で返し、検索の入口が落ちない」ことであり、HTML や暗号形式の完全一致ではない。

### 第1段：核――読む、辿る、探す、API で渡す

**範囲**

- 任意の OKF フォルダを読み取り専用で開く。
- frontmatter と本文を分離し、タイトル、概要、タグ、状態、著者、関連文書などを正規化する。
- `index.md` のリンク順でサイドバーと一覧を構成する。
- 文書ページで Markdown を描画し、メタデータ、タグ、関連リンク、内部リンクを表示する。
- `/search` 相当の検索画面と検索結果 API を持つ。
- `/recent`、`/tags`、`/authors` の読み取り専用版を持つ。
- `/api/index.json` と `/api/chunks.json` を返す。
- 検索は pat-okf-agent と共有する検索コアを使い、日本語入口には文字 bi-gram を使う。
- ローカル利用を既定とし、外部公開や書き込み API は持たない。

**この段を先にする理由**

- SimpleWiki の中心価値は、蓄えた OKF をその場で読め、辿れ、探せることにある。
- 検索と API が安定すれば、静的出力、RAG、他のビューアは同じ部品を再利用できる。
- 書き込みを外すことで、表示順、検索、描画の互換性だけを先に検証できる。

**第1段の完了条件の案**

- 本家のサンプルと実 KB の両方を開ける。
- `index.md` の順序、未登録文書の補完、リンク切れ時の扱いがフィクスチャと一致する。
- 検索のベースラインで、日本語の言い換えが「入口で全滅」しない。
- chunks が見出し境界を保ち、元文書への参照を返せる。
- Drive マウント上の KB でも、実用上問題になる再走査や陳腐化が起きないことを測る。

### 第2段：配る、点検する、安全に同期する

**範囲**

- 静的 HTML エクスポート。通常の複数ファイル出力と、必要なら単一 HTML。
- メンテナンス画面。古い文書、下書き、deprecated、リンク切れなどの点検結果を表示する。
- 索引の再構築、キャッシュ状態、キャッシュ消去などの運用操作。
- `Update-WikiTags.ps1` 相当のタグ同期。最初は差分表示／DryRun のみとし、書き込みは明示的な別操作にする。
- 設定の読み取りと、書き込みを伴わない範囲の設定画面。

**理由**

- 静的出力は、本家で推奨経路の一つであり、サーバーを常駐させず KB を渡せる。
- 点検とタグ同期は KB を育てる運用に直結するが、文書書き込みを伴うため、読み取り核が安定してから扱う方が安全である。

### 第3段：エディタと履歴

**範囲**

- 新規作成、YAML／本文の分離編集、RAW YAML 編集。
- 保存、削除、画像など添付ファイルのアップロード。
- 世代バックアップ、履歴表示、復元。
- 編集 ON/OFF と、サーバー側でも書き込みを拒否する読み取り専用モード。
- 同時編集、競合検出、原子的な保存、パストラバーサル防止。

**理由**

- エディタは利便性が高い反面、正本である Markdown を直接壊し得る。認証、権限、競合、復旧の設計が核とは別に必要になる。
- OKF ビューアとしての価値は読み取りだけでも成立するため、後段でよい。

### 第4段：RAG チャット

**範囲**

- Fast RAG：検索結果と chunks を文脈にして一度で回答する。
- Agentic RAG：`search_okf`、`lookup_glossary`、`read_doc`、`get_linked_docs` を使い、探索過程を表示する。
- SSE ストリーミング、会話履歴、現在開いている文書の文脈。
- OpenAI 互換エンドポイント、Ollama、LM Studio などへの接続抽象。
- API キーは OS の秘密管理へ置き、設定ファイルへ平文で残さない。

**理由**

- RAG は検索と chunks の品質に依存する。土台より先に作ると、検索の問題と生成の問題を切り分けられない。
- LLM 接続、費用、秘密管理、プロンプト、履歴保持など、Wiki 本体とは別の責務が多い。

### 第5段：3D ステラ

**範囲**

- 文書ノードの座標計算、時間軸、共通タグ・リンクの星座表示。
- 3D、意味マップ、タイムラインの視点切替。
- ノード詳細と元文書への遷移。

**理由**

- 俯瞰と発見には面白さがあるが、KB を読む・探すという核の代替にはならない。
- 座標計算と描画性能は独立した設計課題であり、核の互換性を遅らせる理由がない。

### 対象外として切り分けるもの：アクティベーション

- 本家のアクティベーションは、特定 PC 向けに API キー等を配るための仕組みであり、Wiki の知識機能ではない。
- マシン指紋、DPAPI、Windows のマザーボード UUID などプラットフォーム依存が強く、Python／Linux で同じ意味を再現できない。
- Python版では作らないことを既定案とし、秘密の配布が必要になった時点で、対象 OS と脅威モデルを定めて別設計にする。

## 3. 検索コアの共有設計

### 3.1 共有する境界

共有するのは HTTP や画面ではなく、次の純粋な入出力である。

- **文書レコード**：相対パス、種別、title、description、tags、status、本文、見出し、リンク、用語などの正規化済みフィールド。
- **索引**：文書レコードから作る検索用索引、更新検知に必要なファイル指紋、索引の版。
- **クエリ解析**：語句、フレーズ、除外語、範囲指定、言語ごとの分割。
- **スコア計算**：一致したフィールド、語、フレーズ、スコア内訳を返す。画面表示用の文字列には依存しない。
- **結果整形**：順位、スニペット、ヒット箇所、関連リンクを返すための共通データ。
- **評価フィクスチャ**：クエリ、期待文書、期待する順位帯、スコア内訳の性質を両プロジェクトで共有する。

逆に、次は共有しない。

- HTTP ルーティング、HTML、CSS、JavaScript。
- SimpleWiki 固有の設定画面やエディタ。
- pat-okf-agent 固有の取り込み、検証、バッチ、候補選定。
- 特定 KB の synonyms やタグ方針そのもの。これらは入力データとして渡し、検索コアへ焼き込まない。

### 3.2 置き場所の選択肢

| 選択肢 | 利点 | 難点 |
|---|---|---|
| **A. pat-okf-agent 内に共有コアを置き、SimpleWiki Python版が使う** | 検索再設計が現在進んでいる場所と一致する。最初は一つの実装・一つのテストで済み、実 KB の評価をすぐ回せる。境界を保てば後から抽出できる | pat-okf-agent の変更速度やリリースに SimpleWiki が引っ張られる。Web サーバーの都合でツールキット側 API が歪む危険がある。依存方向と版指定を厳密にしないと壊れやすい |
| **B. 独立した検索／OKF コアパッケージを作り、両方が使う** | 責務と公開 API が最もきれい。版管理、再利用、テストの独立性が高い。将来 BlackClaw など別の読み手も使える | 最初から抽出、配布、互換性維持のコストがかかる。再設計の途中で境界を固定すると、変更のたびに二つのリポジトリを触ることになる |
| **C. 各プロジェクトに実装を持ち、仕様とテストだけ共有する** | 各製品が自由に最適化できる | 実装がずれ、片方で直した検索の癖が他方に残る。今回「部品を共有する」目的に合わない |

### 3.3 推奨

**推奨は A を入口にし、B を抽出先として予約する段階方式である。**

1. まず pat-okf-agent 内に、HTTP や CLI から独立した検索コアの境界を作る。
2. スコア、分割、結果型には版を持たせ、SimpleWiki Python版は「検索コアの公開境界」だけを使う。
3. 両方で同じ評価フィクスチャを通し、スコア内訳まで比較できる状態にする。
4. 利用箇所が pat-okf-agent と SimpleWiki の二つで安定し、公開 API の変更頻度が下がったら、独立パッケージ化を判断する。

この順序なら、再設計中の検索を早く SimpleWiki でも試せる一方、早すぎるパッケージ分割で境界を誤固定しない。独立化の判断条件は、少なくとも「文書モデルと検索結果型が大きな変更なく一つの開発サイクルを越える」「両側のテストが同じフィクスチャで安定する」こととする。

### 3.4 スコアの扱い

- SimpleWiki の数値は設計の出発点であり、正解として固定しない。
- 写すのは「フレーズを強く見る」「タイトル／タグ／概要／本文で証拠の強さを分ける」「本文頻度を頭打ちにする」「deprecated など状態は事実として扱う」という構造である。
- pat-okf-agent 側では、概念ノートと特許ノートのように文書種別の比率が偏るため、実測ベースラインと評価クエリで再調整する。
- スコア内訳を API と画面で返せるようにし、なぜその順位になったかを利用者と監査者が追えるようにする。
- 観点別の重要度や話題の優先度は検索コアに保存しない。必要なら呼び出し側が範囲や条件として都度渡す。

## 4. プラットフォーム差の処理

| 本家／Windows・PowerShell | Python／Linux での対応 | 注意点 |
|---|---|---|
| WinRT `WordsSegmenter` による日本語形態素分割 | 日本語の文字種ランに対して文字 bi-gram を使う。英数字列は単語・記号列として扱う | 今夜の決定事項。入口の漏れを防ぐことを優先する |
| 形態素後の助詞ストップワード除去 | そのままは移植しない | bi-gram では助詞を形態素として特定できない。ノイズはフレーズ一致、場所別スコア、範囲指定で抑え、評価で測る |
| WinRT が使えない場合の regex フォールバック | script ごとの分割規則と正規化を明示する | 本家の regex は漢字列を大きな塊として拾うため、bi-gram の代替にはならない |
| Markdig.dll による GFM 描画 | Python の Markdown 描画部品を選定する | 表、脚注、タスクリスト、コードブロック、HTML サニタイズ、Mermaid 用コード保持の互換範囲を先に決める |
| Mermaid の同梱 JS と .NET 画像処理 | まずブラウザ側 Mermaid 描画を基本とし、SVG 化や画像最適化は静的出力段階で扱う | サーバー側画像変換は依存とセキュリティ範囲を広げる |
| `System.Net.HttpListener` | Python の HTTP サーバー／Web フレームワークから選ぶ | 標準ライブラリだけで足りるか、同時接続・SSE・配布方法を考えて決める。第1段は読み取り専用なので過大な枠組みは不要 |
| PowerShell の PSCustomObject と JSON 設定 | Python の辞書／型付きレコードと JSON 設定 | 本家 `config.json` をそのまま読むかは未決。読む場合も未知項目を壊さない |
| DPAPI | Linux では OS の資格情報ストア、権限を絞った秘密ファイル、または環境経由の秘密供給へ置く | DPAPI の復号互換は提供しない。秘密を KB や通常設定へ平文保存しない |
| ポータブル AES の `ENC:` 形式 | 互換が必要か個別に判断する | 暗号形式の互換は利便性より先に、鍵派生、完全性、移行方法を検証する。初期範囲には入れない |
| マザーボード UUID によるマシン指紋 | 直接の等価物はない | ハードウェア ID は OS ごとに取得方法、安定性、プライバシーが異なる。アクティベーション自体を後段／対象外とする |
| Windows パス、ドライブ、区切り文字 | `pathlib` と KB ルートからの相対パスを正とする | URL、Markdown リンク、ファイルシステムの三つの表現を混同しない。パストラバーサル防止はサーバーの必須条件 |
| UTF-8 BOM を前提とする PowerShell 規約 | Markdown と設定は UTF-8 を正とし、BOM の有無を吸収する | Python ソースや出力に BOM 規約は持ち込まない。文字コード不明ファイルの扱いは明示する |
| ファイル更新検知と `.cache` | 更新時刻、サイズ、内容ハッシュの組合せと、対象 KB ごとのキャッシュ識別子 | Drive マウントでは更新時刻や走査速度がローカルと異なる。キャッシュの置き場所と無効化条件を実測する |
| バックアップと上書き | 一時ファイルへの書き込み、検証、原子的置換、世代保持 | エディタ段階の要件。第1段の読み取りサーバーには持ち込まない |
| `.bat`、ドラッグ＆ドロップ、GUI | CLI 引数で対象フォルダを受ける | Linux ではシェルから起動できれば足りる。GUI ランチャーは別需要が出るまで作らない |
| PowerShell 5.1 / Pester 3.4 の検証 | Python のテスト実行系と共有フィクスチャ | 本家テストは文法まで写さず、期待する振る舞いだけを抽出する |

## 5. 置き場所と名前の論点

### 5.1 置き場所の選択肢

| 候補 | 利点 | 難点 |
|---|---|---|
| **新規リポジトリ** | SimpleWiki という製品の境界が明確で、独自のリリース、依存、ドキュメントを持てる。検索コアは外部依存として版を指定できる | リポジトリと配布物が増える。初期は pat-okf-agent との変更調整が煩雑になる |
| **pat-okf-agent 内のアプリ／サブパッケージ** | 検索コアと同じ場所で開発でき、実 KB のテストへすぐ接続できる。初期の摩擦が小さい | ツールキットの責務が Web サーバーまで広がり、依存とリリース周期が混ざる。SimpleWiki の独立した製品性が弱くなる |
| **本家 SimpleWiki リポジトリ内に Python 実装を同居** | 名前、仕様、サンプル、テスト資産を一か所で追える | PowerShell と Python のビルド、CI、リリースが干渉する。本家の Windows 前提の説明と Linux 版の前提を分け続ける必要がある |

**計画上の推奨：** 製品としては新規リポジトリを本命とし、検索コアは当面 pat-okf-agent 側を正本として参照する。新規リポジトリの作成自体は、オーナーが名前と境界を決めるまで行わない。

### 5.2 名前の案

- リポジトリ表示名：`SimpleWiki (Python)`
- リポジトリ名候補：`SimpleWiki-Python`、`simplewiki-python`、`SimpleWikiPy`
- Python パッケージ名候補：`simplewiki`、`simplewiki_py`、`simplewiki-python`

名前は、PyPI や既存プロジェクトとの重なり、Windows 版との関係、コマンド名の短さを合わせて確認してから決める。本メモではどれも確定名として扱わない。

### 5.3 オーナー判断が必要な点

次を決めるまでは、リポジトリ作成や実装へ進まない。

1. 置き場所：新規リポジトリ、pat-okf-agent 内、本家リポジトリ同居のどれか。
2. 製品名、リポジトリ名、Python パッケージ名、CLI コマンド名。
3. 検索コアの正本を pat-okf-agent とする段階方式を採るか、最初から独立パッケージにするか。
4. 本家との互換性の深さ：API 形式と表示順を核とするか、設定ファイルや HTML 構造まで寄せるか。
5. 初期対象 OS と Python 版：Linux を正とする範囲、Windows／macOS を同じ版で支えるか。

## 6. 未決論点の一覧

### 製品・境界

- リポジトリの置き場所と名前、ライセンス表記を本家からどう引き継ぐか。
- SimpleWiki Python版は「本家の移植」として版を合わせるのか、独立した版系列にするのか。
- 第1段の対象を読み取り専用に固定するか、設定変更だけは許可するか。
- 静的エクスポートを第2段へ置く前提でよいか。利用目的によっては第1段と並ぶ可能性がある。

### 検索コア

- pat-okf-agent の検索再設計メモが確定した時点で、本メモの共有境界と突き合わせる必要がある。
- bi-gram の対象範囲：漢字、カタカナ、ひらがな、長音、数字混じり語をどう切り分けるか。
- bi-gram と完全語、フレーズ、synonyms を一つのクエリでどう組み合わせるか。
- スコアの初期値と、SimpleWiki の数値から変更する場合の根拠。
- インデックスをメモリ常駐にするか、ディスクキャッシュを持つか。Drive マウント時の更新検知と初回構築時間。
- 評価クエリの正本をどこに置き、どちらのプロジェクトが変更責任を持つか。

### OKF と描画

- pat-okf-agent の現在の frontmatter と SimpleWiki が補完する frontmatter の差異を、どちらへ寄せるか。
- `description` がない文書の概要生成を、本文先頭、見出し、LLM なしの規則のどれでまかなうか。
- Markdown 方言の互換範囲：表、脚注、タスクリスト、生 HTML、Mermaid、数式、画像パス。
- `index.md` がない KB、壊れたリンク、循環リンク、重複 slug の扱い。
- chunks の分割単位を見出し固定にするか、長文の二次分割を許すか。

### サーバーと運用

- HTTP 実装の依存方針：標準ライブラリ中心か、軽量フレームワークを使うか。
- 同時接続、長い検索、索引再構築中の応答、停止方法。
- ローカル限定を既定とし、LAN 公開時の認証や読み取り専用制御をいつ入れるか。
- 本家 `config.json` の互換読み込みを行うか、Python版専用設定へ移行案内を出すか。
- ログ、キャッシュ、索引の保存先。KB 本体へ書かず、利用者側へ置くのが基本案。

### 後段機能

- エディタでの同時編集、競合、削除、アップロード上限、添付ファイルの検査。
- タグ同期を自動実行せず、差分確認を必須にする運用でよいか。
- RAG の LLM 接続先、費用、履歴保持、回答への引用形式。
- 秘密管理を OS ごとにどう統一するか。DPAPI／`ENC:` 互換を本当に必要とするか。
- アクティベーションは Python版の対象外で確定できるか。
- 3D ステラを最終段とするか、静的エクスポートの表現として先に小さく試すか。
- 多言語 UI を第1段から構造だけ入れるか、日本語専用で始めるか。

## 7. 次に決める順序

1. **置き場所と名前**を決める。
2. **検索コアの正本と境界**を、pat-okf-agent の検索再設計メモと突き合わせて確定する。
3. **第1段の互換範囲**を、API、表示順、検索、描画の受け入れフィクスチャとして固定する。
4. HTTP 実装と Markdown 描画の依存方針を決める。
5. その後に初めて、リポジトリと最小実装へ進む。
